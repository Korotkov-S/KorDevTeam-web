# SEO change-effect measurement

The Changes screen `/admin/seo/changes/` reads saved measurements; opening it never calls search providers or writes evaluations. `list_seo_change_effects` exposes the same paginated read model under seo:read; `history=true` requires changeId. `get_seo_page_control` exposes the complete published registry with source-specific index facts.

After the existing daily free collection and index-audit synchronization, an operator/heartbeat may run `node server/seo-effects-evaluate.mjs` inside the strictly verified active web container. Resolve the unique current-slot marker and verify private immutable-image state, actual image/revision and health as documented in seo-page-control.md. The CLI reads saved evidence only and appends hash-deduplicated snapshots, printing inserted/unchanged or the safe seo_effect_evaluation_failed code. It does not call providers, paid rank APIs, recrawl/indexing services, publishing or core activation. Retry this operation only, not already completed provider collection.

Each change/source has a frozen assigned active-key cohort. Each 7/14/28 checkpoint freezes its first fully covered baseline, recording actual capture time; existing changes are explicitly retrospective. Incomplete attempts remain in history and may be supplemented by later data. Removed/reassigned cohort keys make comparisons incompatible; new keys do not silently join. The source calendar day containing application is omitted. Baseline is the immediately preceding N full days; after is the N full days starting the following source-calendar day (Yandex Moscow, Google Los Angeles).

Successful collection-run windows must cover every date in both periods. A latest source failure/running/partial attempt, or age over36h, defers conclusions. Evaluation acquires collector locks and never reads a concurrently refreshed partial dataset. Correct current publication/index evidence and a post-application crawl are prerequisites. Explicit live HTTP/noindex/robots/canonical/error failures block directional results even if an older search index still reports indexed. The change must identify the same content entry and a known change-time version; an unknown version is pending_provenance, never inferred from the current publication. Later same-page content journal changes or version drift mark confounding; other-type operational events do not. These checks do not prove every impression was generated by the new version or that the change caused a result.

Engineering policy v1: Russia only; desktop/mobile, plus Google tablet; exclude device=all and city duplicates. Freeze query IDs, compute per-query impression-weighted mean positions, then equally weight those query means. Every key needs100 impressions in each period; minimum effect1 position. Raw clicks/impressions/CTR have explicit denominators and refer to the selected query dataset, not total traffic (providers may omit queries). Zero rows in a successfully covered period are low sample, never a rank of zero or outside top100. Exact weekly Search API controls remain separate.

Seven days are an early signal,14 intermediate,28 final observational window. Missing historical coverage may prevent a28-day verdict; source publication lag also delays eligibility after calendar maturity. pending_period/source/coverage/refresh and insufficient_data are not a lost experiment. not_applicable covers other-type operational journal events; they must not be represented as content hypotheses. No result automatically changes a page or approves a recommendation. New content needs a human decision and a separate journaled change, then another measured window.
