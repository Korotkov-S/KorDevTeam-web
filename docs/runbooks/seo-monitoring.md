# SEO-мониторинг KorDevTeam

Система ежедневно забирает только официальные данные Яндекс Вебмастера и Google Search Console, сохраняет неизменяемые дневные срезы в PostgreSQL и показывает их на `/admin/seo/`. Метрика называется «Средняя позиция»: это агрегат источника, а не проверка живой выдачи. Сборщик не использует платный SERP API и не парсит поисковую выдачу.

## Доступы к источникам

### Яндекс Вебмастер

1. Создайте OAuth-приложение Яндекса и выдайте ему только доступ на чтение данных Вебмастера.
2. Убедитесь, что нужный подтверждённый сайт виден этой учётной записи.
3. Запишите OAuth-токен в `YANDEX_WEBMASTER_OAUTH_TOKEN` и точный идентификатор подтверждённого host в `YANDEX_WEBMASTER_HOST_ID`.
4. Установите `SEO_YANDEX_ENABLED=true` только после заполнения обоих значений.

При каждом запуске сборщик сначала читает официальный каталог регионов конкретного host. Россия, Москва, Санкт-Петербург, Новосибирск, Екатеринбург, Казань, Нижний Новгород и Краснодар сопоставляются по официальным названиям. Отсутствующий город остаётся в интерфейсе как «данных пока нет»; выдуманный geobase ID никогда не подставляется.

### Google Search Console

1. Создайте отдельную service account в Google Cloud.
2. Добавьте её email в нужное свойство Search Console с правом чтения.
3. Укажите точное свойство в `GOOGLE_SEARCH_CONSOLE_SITE_URL`: HTTPS URL-prefix либо `sc-domain:example.com`.
4. Сохраните email в `GOOGLE_SEARCH_CONSOLE_CLIENT_EMAIL`.
5. Кодируйте PKCS8 PEM локально, не печатая ключ в общий журнал:

   ```bash
   GOOGLE_SEARCH_CONSOLE_PRIVATE_KEY_B64="$(base64 < service-account-private-key.pem | tr -d '\n')"
   export GOOGLE_SEARCH_CONSOLE_PRIVATE_KEY_B64
   ```

6. Установите `SEO_GOOGLE_ENABLED=true` только после заполнения всех трёх значений.

Google собирается только по стране `RUS` и устройствам. Городских срезов Search Console не предоставляет, поэтому в Google-режиме их нет ни в запросах, ни в интерфейсе.

### Яндекс Метрика

Яндекс Метрика используется отдельно от Вебмастера: она даёт поведение органических посетителей — посетителей, визиты, просмотры страниц, отказы, глубину и среднее время. Получите OAuth-токен с правом чтения нужного счётчика, затем укажите его числовой идентификатор:

```bash
SEO_YANDEX_METRIKA_ENABLED=false
YANDEX_METRIKA_OAUTH_TOKEN=
YANDEX_METRIKA_COUNTER_ID=
```

Сначала оставьте источник выключенным. Проверьте доступ командой `--check --source=metrika`, затем включите `SEO_YANDEX_METRIKA_ENABLED=true` и выполните первый импорт. Сборщик запрашивает только органический трафик без роботов, требует полные несэмплированные ответы и не сохраняет токен в базе или журнале.

### Контрольные позиции Яндекса

Контрольный снимок органической выдачи собирается отдельно от Яндекс Вебмастера через официальный Yandex Search API. Создайте сервисный аккаунт с ролью `search-api.webSearch.user`, выпустите API-ключ с областью действия `yc.search-api.execute` и укажите:

```bash
SEO_YANDEX_SEARCH_ENABLED=false
YANDEX_SEARCH_API_KEY=
YANDEX_SEARCH_FOLDER_ID=
SEO_TARGET_HOST=kordev.team
```

Сначала оставьте переключатель выключенным. После заполнения защищённого environment-файла выполните `--check --source=yandex-rank`, затем включите `SEO_YANDEX_SEARCH_ENABLED=true`. Ключ нельзя печатать в журнал, передавать в argv или сохранять в базе.

Search API снимает первые 100 органических результатов отдельно для России, Москвы, Санкт-Петербурга, Новосибирска, Екатеринбурга, Казани, Нижнего Новгорода и Краснодара, для desktop и mobile. Это контрольный снимок конкретного запуска, а не средняя позиция по показам. Google таким способом не проверяется.

Файл `/etc/kordevteam/operations.env` должен принадлежать оператору и иметь mode `0600`. Не передавайте OAuth-токен, PEM/base64-ключ или MCP-токен в Git, задачи, чат или командную строку, которая сохраняется в общей истории.

## Проверка и первый импорт

После миграции `0005` и до включения таймера проверьте доступы из того же неизменяемого worker image:

```bash
docker compose -f deploy/docker-compose.team.yml --profile seo run --rm --no-deps seo-job node server/seo-collect.mjs --check
```

Первый импорт:

```bash
bash scripts/run-seo-collect.sh
```

Отдельный повтор источника:

```bash
docker compose -f deploy/docker-compose.team.yml --profile seo run --rm --no-deps seo-job node server/seo-collect.mjs --source=yandex
docker compose -f deploy/docker-compose.team.yml --profile seo run --rm --no-deps seo-job node server/seo-collect.mjs --source=google
docker compose -f deploy/docker-compose.team.yml --profile seo run --rm --no-deps seo-job node server/seo-collect.mjs --source=metrika
docker compose -f deploy/docker-compose.team.yml --profile seo run --rm --no-deps seo-job node server/seo-collect.mjs --source=yandex-rank
```

Backfill намеренно ограничен скользящим окном: Яндекс Вебмастер и Метрика повторно импортируют 14 полных дней до вчерашней даты, Google — 14 финализированных дней с отставанием в три дня. Повторный запуск обновляет те же строки и не удаляет ранее сохранённые наблюдения. Произвольного многолетнего backfill в production-команде нет: для него требуется отдельный проверенный одноразовый запуск, чтобы не превысить квоты источника.

## Ежедневный запуск

Установите unit-файлы из `deploy/systemd/`, затем включите таймер:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now kordevteam-seo-collect.timer
systemctl status kordevteam-seo-collect.timer
systemctl list-timers kordevteam-seo-collect.timer
journalctl -u kordevteam-seo-collect.service --since today
```

Сбор начинается в 07:30 Europe/Moscow с небольшой случайной задержкой и должен закончиться до агентского анализа в 09:00. PostgreSQL advisory lock не допускает двух одновременных импортов одного источника. Яндекс и Google независимы: ошибка одного не откатывает второй.

## MCP-токен ежедневного агента

На `/admin/mcp/` выпустите новый отдельный токен «SEO heartbeat» только с правами:

- `seo:read` — сводка, запросы, журнал изменений и рекомендации;
- `seo:write` — создание рекомендаций, регистрация уже выполненных изменений и смена статуса рекомендаций.

Не добавляйте этому токену `content:write` или `content:publish`. SEO-инструменты сами по себе не могут менять публичные тексты. Подключение endpoint и безопасное хранение Bearer-токена описаны в `docs/runbooks/mcp-content-access.md`.

## Как читать состояния

- «Не настроено» — source выключен; внешний запрос не выполняется, история остаётся в базе.
- «Данных пока нет» — источник доступен, но ещё не вернул наблюдений по выбранному срезу, либо Яндекс не подтвердил желаемый регион.
- Google с задержкой в несколько дней — штатное поведение финализированных Search Console данных. Вчерашняя дата не обязательна.
- `partial` — часть регионов/устройств Яндекса сохранена, но хотя бы один срез не завершился. Успешные строки сохраняются и повторно обновятся на следующем запуске.
- `429` / `seo_*_retryable` — квота или временная ошибка. Сборщик делает ограниченные повторы; проверьте следующий запуск и квоты, не запускайте бесконечный цикл вручную.
- `seo_*_auth_failed` — проверьте право учётной записи, точный host/property, срок действия токена и ротацию ключа. Такая ошибка не повторяется автоматически в рамках одного запуска.
- Пустой график не равен нулю. Отсутствующий день остаётся разрывом линии.

## Ротация и отключение

Для безопасной ротации сначала подготовьте новый доступ, замените секрет в mode-0600 environment-файле, выполните `--check`, запустите один source-specific импорт и только затем отзовите старый доступ. Секреты не сохраняются в PostgreSQL и не попадают в ответы админки/MCP.

Чтобы временно остановить источник, установите соответствующий флаг `SEO_YANDEX_ENABLED=false`, `SEO_GOOGLE_ENABLED=false`, `SEO_YANDEX_METRIKA_ENABLED=false` или `SEO_YANDEX_SEARCH_ENABLED=false` и повторно запустите `--check`. Это не удаляет историю метрик, контрольных позиций, изменений или рекомендаций. Не очищайте таблицы ради повторного импорта: upsert рассчитан на безопасный повтор.

После изменения расписания или credentials проверьте `/admin/seo/`, дату последних данных, `systemctl status` и безопасные коды ошибок в журнале. Реальные метрики считаются подключёнными только после успешного `--check` и первого импорта против подтверждённых production-свойств.
