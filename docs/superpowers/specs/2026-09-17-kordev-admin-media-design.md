# Админка KorDevTeam и медиатека — проектная спецификация

**Дата:** 2026-09-17

**Статус:** ожидает подтверждения перед подготовкой плана реализации

**Связанный документ:** `docs/superpowers/specs/2026-09-11-kordev-seo-conversion-design.md`

## 1. Результат этапа

Создать новую защищённую админку `/admin/`, через которую один администратор сможет управлять статьями, кейсами, услугами, FAQ, общими страницами, SEO-полями, связями материалов, настройками сайта и публичными изображениями. PostgreSQL становится единственным рабочим источником контента, а Timeweb S3 — единственным рабочим хранилищем публичных изображений.

Переход выполняется напрямую, без staging-поддомена и без автоматического переключения production. До ручного переключения новая версия проверяется в неактивном blue/green-слоте. Текущие SQLite/SQL.js-файлы и локальные изображения сохраняются не менее 30 дней только для аварийного отката; новая админка никогда в них не пишет.

## 2. Границы этапа

В этап входят:

- серверная авторизация администратора;
- защищённые SSR-маршруты и действия React Router;
- редактор всех существующих типов контента;
- черновики, предварительный просмотр, публикация, снятие с публикации, восстановление ревизии и жёсткое удаление;
- медиатека публичных изображений в Timeweb S3;
- перенос текущих изображений и ссылок на них;
- отключение прежних изменяющих API после подтверждённой миграции;
- автоматические проверки безопасности, целостности и пользовательских сценариев;
- сценарий ручного переключения и безопасного отката.

В этап не входят:

- редизайн коммерческих страниц и написание их контента;
- контент-аудит `оставить / расширить / объединить / noindex / 410`;
- интерфейс просмотра заявок и CRM-функции в админке;
- изменение уже реализованного приёма заявок;
- настройка аналитических целей и cookie-баннера;
- отдельный журнал действий администратора;
- английская версия сайта;
- автоматическое production-переключение.

## 3. Подтверждённые решения

- Админка остаётся по адресу `/admin/`, отдельный поддомен не создаётся.
- Администратор входит по логину и паролю.
- Первый пользователь создаётся только CLI-командой на доверенной машине. В коде и конфигурации нет стандартного или резервного пароля.
- Контент хранится только в PostgreSQL. Публикация не требует сборки сайта.
- Все изменения защищены серверной сессией, CSRF-проверкой и оптимистической блокировкой по версии записи.
- Удаление контента — жёсткое, с явным подтверждением. Вместе с записью каскадно удаляются её ревизии и связи.
- Отдельный audit log не создаётся. Автор содержательного изменения сохраняется в ревизии.
- Публичные изображения загружаются в Timeweb S3, получают адаптивные варианты и могут раздаваться через CDN провайдера.
- Админка принимает JPG, PNG и WebP. SVG через админку не загружается.
- Старые английские материалы не архивируются и не переносятся.
- Обычная светлая и тёмная темы сайта сохраняются; интерфейс админки поддерживает обе.

## 4. Исходное состояние и ограничения

В PostgreSQL уже существуют таблицы `admin_users`, `content_entries`, `content_revisions`, `content_relations`, `media_assets` и `site_settings`. Публичные SSR-маршруты уже читают опубликованный контент через `src/server/content/`.

При этом текущая страница `src/pages/AdminPage.tsx` обращается к старым Express API. Маршруты `server/routes/posts.js`, `projects.js`, `content.js` и `admin.js` изменяют SQL.js/SQLite и файловые данные. В текущей карте React Router нет защищённой ветки `/admin/`, а модулей `src/server/auth/` и `src/server/media/` ещё нет.

Реализация расширяет существующую PostgreSQL-модель и не создаёт параллельную CMS. Маршруты React Router отвечают за HTTP и представление; SQL, криптография, S3 и правила публикации остаются в серверных сервисах.

## 5. Целевая архитектура

```text
Браузер администратора
  -> /admin/*
  -> React Router SSR loader/action
     -> src/server/auth/     сессии, пароль, CSRF, rate limit
     -> src/server/content/  записи, связи, ревизии, публикация
     -> src/server/media/    проверка файлов, варианты, Timeweb S3
     -> PostgreSQL

Публичный SSR
  -> src/server/content/
  -> только status = published
  -> PostgreSQL + публичные S3/CDN URL
```

Новые границы модулей:

- `src/server/auth/` — конфигурация, scrypt, сессии, CSRF, ограничение входа, CLI bootstrap;
- `src/server/admin/` — схемы форм, права на действия, безопасные коды ошибок и координация редактора;
- `src/server/media/` — проверка изображений, генерация вариантов, ключи объектов, S3-адаптер, компенсация и поиск сирот;
- `src/routes/admin/` — SSR-экраны, loaders и actions без прямого SQL/S3;
- `scripts/` — повторяемые команды bootstrap, dry-run миграции и применения проверенного пакета миграции.

Все импорты серверных модулей должны оставаться вне клиентского bundle. Пароли, password digest, сырой session token, hash сессии и серверные ключи не попадают в loader-ответы, HTML, логи или browser storage. CSRF token — единственное исключение: сервер передаёт его только внутри защищённого admin-ответа, привязывает к текущей сессии и никогда не сохраняет в browser storage.

## 6. Маршруты и навигация

Канонические маршруты админки:

- `/admin/login/` — вход;
- `/admin/` — обзор и быстрый переход к черновикам;
- `/admin/content/:kind/` — список одного типа контента;
- `/admin/content/:kind/new/` — создание;
- `/admin/content/:kind/:id/` — редактирование;
- `/admin/media/` — медиатека и загрузка;
- `/admin/settings/` — структурированные настройки сайта.

Допустимые значения `:kind`: `service`, `case`, `article`, `page`, `faq`. Неизвестный тип возвращает 404 до обращения к репозиторию.

В desktop-режиме используется боковая навигация, на узком экране — доступная клавиатурой выдвижная панель. Списки поддерживают поиск, фильтр статуса и фильтр типа; на главном экране есть быстрый переход к черновикам.

Все ответы `/admin/*`, включая ошибки и вход, содержат:

- `X-Robots-Tag: noindex, nofollow`;
- `Cache-Control: no-store`;
- запрет встраивания через CSP `frame-ancestors 'none'`;
- CSP без `unsafe-eval`; inline-скрипты допускаются только с nonce, если они необходимы SSR-рантайму;
- `Referrer-Policy: same-origin` и `X-Content-Type-Options: nosniff`.

## 7. Модель данных

### 7.1 Существующие таблицы

Сохраняются `admin_users`, `content_entries`, `content_revisions`, `content_relations`, `media_assets` и `site_settings`. Изменения PostgreSQL-схемы для этого этапа выполняются только добавочными Drizzle-миграциями: существующие таблицы и поля не переименовываются и не удаляются.

`content_entries.version` — обязательная версия оптимистической блокировки. Каждое успешное содержательное изменение увеличивает её ровно на один и создаёт полный снимок в `content_revisions` в той же транзакции. Публикация, снятие с публикации и восстановление ревизии считаются содержательными изменениями.

`content_revisions.admin_user_id` указывает автора действия. Снимок включает поля записи, статус, связи и media references. При восстановлении старой ревизии история не перематывается назад: создаётся новая текущая версия со снимком выбранной ревизии.

`media_assets` хранит оригинальный объект, checksum, MIME, размер, габариты, alt-текст и JSONB-карту вариантов. В таблицу добавляются `processing_version`, `version` и признак декоративного изображения. Составной уникальный индекс `(checksum, visibility, processing_version)` гарантирует безопасную дедупликацию. Для этого этапа версия алгоритма равна `1`; её изменение в будущем создаст новый набор вариантов без перезаписи старых объектов.

В `site_settings` добавляется `version`. Изменение настройки или метаданных media asset выполняется только с ожидаемой версией и атомарно увеличивает её на один. Создание новой записи, вход, выход и техническая очистка истёкших данных не требуют клиентской версии.

Добавляется `content_media_refs`:

- `entry_id` с каскадным удалением;
- `media_id` с запретом удаления используемого media asset;
- стабильный `field_path`, например `body_md:0`, `og_media_id` или `payload.gallery.2`;
- составной первичный ключ `(entry_id, media_id, field_path)`.

Редактор синхронизирует эту таблицу в той же транзакции, что и запись контента. Markdown хранит изображение как `![alt](media:<uuid>)`, а media-поля payload — как UUID, не как S3 URL. Presentation-слой разрешает такие ссылки через `media_assets` и централизованный CDN URL builder. Благодаря этому проверка ссылок и запрет удаления не зависят от поиска подстрок в JSON/Markdown.

### 7.2 Сессии администратора

Добавляется `admin_sessions`:

- UUID `id`;
- `admin_user_id` с каскадным удалением;
- уникальный `token_hash`;
- `csrf_hash`;
- `created_at`;
- `last_seen_at`;
- `expires_at`;
- nullable `revoked_at`.

Индексы позволяют быстро искать активную сессию и удалять истёкшие записи. Сырые токены никогда не сохраняются в БД.

### 7.3 Ограничение попыток входа

Для авторизации используется отдельная таблица `admin_auth_limits`, не связанная с лимитами формы заявки:

- HMAC-идентификатор субъекта;
- тип `ip`, `login` или `global`;
- начало фиксированного окна;
- число неудач;
- срок автоматического удаления.

Идентификаторы IP и логина вычисляются HMAC-SHA-256 отдельным серверным секретом. Открытые IP и введённые логины не сохраняются. Базовое ограничение: не более пяти неудачных попыток за 15 минут отдельно для IP и логина и не более 50 неудачных попыток за 15 минут глобально для всей установки. Успешный вход очищает bucket логина, но не скрывает системную атаку по IP. Истёкшие buckets удаляются пакетами не более 500 строк за один запуск.

## 8. Авторизация и сессии

CLI bootstrap принимает логин интерактивно или через безопасный stdin, проверяет отсутствие активного администратора с таким логином и сохраняет scrypt digest. Пароль не передаётся аргументом командной строки и не выводится в лог.

Пароль должен иметь длину от 14 до 256 Unicode-символов. Для новых digest используется:

- случайная salt 32 байта;
- scrypt `N=32768`, `r=8`, `p=1`;
- выход 64 байта;
- `maxmem=64 MiB`;
- сравнение постоянного времени.

При успешном входе сервер генерирует случайный token не менее 32 байт и отдельный CSRF token. Браузер получает token только в cookie `__Host-kordev_admin` с атрибутами `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/` и без `Domain`. PostgreSQL хранит HMAC-SHA-256 token с отдельным серверным secret. Абсолютный срок сессии — 12 часов; обращение не продлевает его сверх исходного `expires_at`.

CSRF работает по схеме synchronizer token: сервер хранит только hash, а значение передаёт защищённой странице в hidden field; fetch-действия дублируют его в `X-CSRF-Token`. Все изменяющие actions требуют одновременно действующую сессию, корректный CSRF token, same-origin `Origin`/`Sec-Fetch-Site` и ожидаемый HTTP-метод. Проверка Origin не заменяет CSRF token.

Выход отзывает текущую сессию и очищает cookie. Смена пароля отзывает все сессии пользователя. Неактивный администратор не может продолжить существующую сессию. Ошибка входа одинакова для неизвестного логина, неверного пароля и неактивного пользователя.

При истечении сессии безопасный GET возвращает на `/admin/login/` с локальным return path. Return path принимается только как нормализованный путь внутри `/admin/`; абсолютные URL и protocol-relative значения отбрасываются. Для POST сервер возвращает контролируемую ошибку с предложением войти повторно и не повторяет изменение автоматически.

## 9. Редактор контента

Экран редактирования содержит вкладки «Контент», «SEO», «Связи», «Предпросмотр» и «История». Поля зависят от вида записи, но общий контракт включает slug, заголовок, excerpt, Markdown body, SEO title/description, индексируемость, Open Graph image, типизированный payload и связи.

Основные действия:

- «Сохранить черновик» сохраняет запись со статусом `draft`;
- «Опубликовать» сначала выполняет полную серверную проверку и затем атомарно устанавливает `published`;
- «Снять с публикации» создаёт новую draft-версию;
- «Восстановить» копирует выбранный снимок в новую текущую версию;
- «Удалить» требует повторного явного подтверждения с названием записи и выполняет жёсткое удаление;
- изменение связей, статуса, SEO и Open Graph image входит в ту же транзакцию записи и ревизии.

Вкладка предпросмотра отправляет текущее состояние формы в защищённый admin action и использует тот же серверный presentation-код, что и публичный SSR. Предпросмотр не сохраняет данные и не создаёт отдельный публичный URL или preview token. Action требует действующую сессию и CSRF, а ответ получает `no-store` и `noindex` и не добавляется в sitemap.

Каждая форма изменения существующей сущности передаёт исходный `version`. Сервер обновляет запись только при совпадении версии. Если другой запрос уже изменил запись, action возвращает 409 и показывает текущую серверную версию без автоматической перезаписи. Администратор может скопировать свой текст, обновить страницу и применить изменения вручную.

При validation error введённые данные сохраняются в форме, а ошибки выводятся рядом с соответствующими полями и в доступном общем резюме. Переход со страницы с несохранёнными изменениями вызывает предупреждение. Кнопки «Сохранить черновик» и «Опубликовать» визуально и семантически разделены.

После публикации, снятия с публикации, восстановления или удаления синхронно инвалидируются соответствующие content/cache и sitemap keys. Публичный ответ никогда не показывает draft.

## 10. Медиатека и обработка изображений

### 10.1 Проверки

Одна загрузка принимает JPG, PNG или WebP размером не более 20 MiB и не более 40 мегапикселей после декодирования. Сервер проверяет magic bytes, фактический MIME, успешное безопасное декодирование, ширину/высоту и лимит пикселей; расширение и клиентский `Content-Type` не считаются доказательством формата. Метаданные, не нужные для отображения, удаляются при создании вариантов.

Оригинал сохраняется, а сервер формирует WebP-варианты шириной 640, 1280 и 1920 пикселей без увеличения исходника. Повторяющиеся фактические размеры не создаются. Карта вариантов содержит ключ, MIME, ширину, высоту и byte size. Alt-текст редактируется отдельно и обязателен при выборе изображения для содержательного блока; для явно декоративного изображения сохраняется отдельный признак, а не пустота по умолчанию.

### 10.2 Ключи и кеширование

Публичные объекты получают content-addressed ключи на основе SHA-256 проверенного содержимого и версии алгоритма обработки, например `media/v1/<prefix>/<digest>/<width>.webp`. Ключи не содержат исходное имя, персональные данные или путь локального файла. Одинаковая загрузка повторно использует уже существующий набор объектов и строку медиатеки.

Объекты доступны через настроенный публичный Timeweb S3/CDN base URL и получают длительное immutable-кеширование. В БД сохраняются ключи, а публичные URL строятся централизованно из конфигурации, чтобы смена CDN не требовала переписывать контент.

### 10.3 Согласованность S3 и PostgreSQL

S3 и PostgreSQL не имеют общей транзакции, поэтому сохранение выполняется в таком порядке:

1. файл помещается во временный приватный объект;
2. сервер проверяет и декодирует его, вычисляет checksum и формирует варианты;
3. финальные content-addressed объекты загружаются и проверяются через S3;
4. одна PostgreSQL-транзакция создаёт или переиспользует `media_assets`, прикрепляет media ID к контенту, создаёт ревизию и увеличивает версию;
5. временный объект удаляется при любом исходе.

Если S3 не подтвердил финальные объекты, PostgreSQL-транзакция не начинается. Если БД отклонила транзакцию, сервис удаляет только те финальные объекты, которые создала именно эта операция и которые после повторной проверки не имеют ссылки в БД. Уже существующие дедуплицированные объекты не удаляются. Ошибка компенсации регистрируется как безопасная структурированная ошибка, а объект подбирает последующий orphan sweep.

Объект нельзя удалить через админку, пока на него ссылается `content_media_refs`, `content_entries.og_media_id` или другая строка медиатеки. Жёсткое удаление строки и объектов разрешено только при нулевом числе ссылок, проверенном в PostgreSQL-транзакции с блокировкой строки `media_assets`. Периодический orphan sweep удаляет лишь объекты старше защитного окна в 24 часа, которых нет в БД и которые не принадлежат активной загрузке или миграционному batch.

## 11. Миграция текущего контента и изображений

Миграция повторяема и разделена на dry-run и apply.

Dry-run:

- читает уже импортированные PostgreSQL `body_md`, `payload`, `og_media_id` и связанные поля;
- читает только русские legacy Markdown/JSON/SQLite-источники, необходимые для сверки;
- находит ссылки на локальные и внешние изображения;
- нормализует путь без выхода за разрешённые каталоги;
- вычисляет checksum, проверяет доступность и формат;
- определяет дедупликацию, конфликт, отсутствующий или нечитаемый файл;
- формирует machine-readable JSON-отчёт и человекочитаемое резюме;
- не изменяет PostgreSQL, S3 и исходные файлы.

Отчёт содержит batch ID, checksum входного набора и точные количества: записей по типам и статусам, ревизий, связей, обнаруженных media references, уникальных файлов, дублей, внешних URL, отсутствующих файлов, ошибок декодирования и предполагаемых замен.

Apply принимает только ранее созданный неизменённый отчёт и его checksum. Для каждого уникального файла он создаёт проверенные content-addressed объекты, затем транзакционно создаёт/переиспользует `media_assets`, переписывает Markdown-ссылки в формат `media:<uuid>`, сохраняет UUID в структурированных media-полях и заполняет `content_media_refs`. Команда записывает результат каждого элемента и безопасно возобновляется после остановки: совпавший checksum и уже подтверждённый объект не загружаются повторно.

Перед разрешением переключения отчёт после apply обязан подтвердить:

- равенство ожидаемого и фактического числа контентных записей по типу и статусу;
- сохранение всех ревизий и связей;
- отсутствие неразрешённых локальных media references в публикуемом контенте;
- существование и совпадение checksum каждого объекта из `media_assets`;
- нулевое число необъяснённых пропусков и конфликтов.

Исходные SQLite/SQL.js-файлы, Markdown/JSON и локальные изображения не удаляются миграцией. Английские материалы исключаются из входа и не копируются в PostgreSQL или S3.

## 12. Отключение старой админки

После успешной проверки миграции новый `/admin/` полностью заменяет `src/pages/AdminPage.tsx` и старую Basic/Auth-header схему. Новый образ регистрирует tombstone-обработчики: все изменяющие методы прежних `/api/posts`, `/api/projects`, `/api/content` и `/api/admin` возвращают `410 Gone`, а прежние read-only admin endpoint не регистрируются и возвращают 404. Ни один такой запрос не может писать в SQLite, SQL.js, Markdown/JSON или локальные uploads.

Если старые read-only пути временно нужны предыдущему immutable Docker-образу для отката, они остаются только внутри этого старого образа. Новый образ не использует legacy-хранилище ни для чтения публичного контента, ни для записи.

Автоматическая проверка отправляет запросы ко всем прежним изменяющим endpoint и доказывает, что ни один legacy-файл и SQLite checksum не изменился.

## 13. Ошибки и наблюдаемость

Ожидаемые ответы:

- `400` — некорректная форма или файл;
- `401` — нет действующей сессии;
- `403` — CSRF/origin/action запрещены;
- `404` — запись или допустимый маршрут не найден;
- `409` — конфликт версии или уникального slug;
- `413` — превышен размер загрузки;
- `422` — содержимое не проходит правила публикации;
- `429` — превышен лимит входа;
- `500/503` — внутренняя ошибка или временная недоступность БД/S3.

Пользователь видит русское безопасное сообщение и request ID. В структурированный серверный лог попадают request ID, вид операции, безопасный ID сущности, код результата и длительность. В лог не попадают пароль, cookie/token, CSRF token, HMAC subjects, полный текст черновика, секреты S3 и содержимое файла.

Ошибки загрузки S3 не создают строку `media_assets`. Ошибки PostgreSQL не приводят к частичной публикации, потере предыдущей версии или удалению уже используемого S3-объекта. Незавершённая операция доступна для диагностики по request ID.

## 14. Проверки

### 14.1 Модульные

- scrypt создание/проверка digest и constant-time comparison;
- срок и отзыв сессии, HMAC token, cookie attributes;
- CSRF, Origin и безопасный return path;
- rate limit по IP/login и ограниченная очистка;
- server-only конфигурация и отсутствие секретов в loader payload;
- схемы всех типов контента и правила публикации;
- magic bytes, MIME, пиксели, размер и варианты изображений;
- content-addressed ключи и URL builder.

### 14.2 Интеграционные с PostgreSQL и S3-адаптером

- login/session/logout/password-change;
- одна транзакция записи, связей, ревизии и версии;
- 409 при конкурирующем сохранении без перезаписи;
- восстановление создаёт новую ревизию;
- hard delete каскадно удаляет ревизии и связи;
- S3 failure не создаёт media row;
- DB failure выполняет безопасную компенсацию;
- дедупликация не удаляет общий объект;
- media deletion запрещена при ссылках;
- публикация инвалидирует public content и sitemap cache.

### 14.3 SSR и браузерные сценарии

- все admin-ответы имеют `noindex`, `no-store` и anti-framing headers;
- неавторизованный пользователь не читает и не меняет данные;
- вход, создание черновика, preview, публикация, снятие с публикации, восстановление и удаление;
- загрузка изображения, выбор из медиатеки и отображение публичного варианта;
- сохранение введённого текста при ошибке;
- предупреждение о несохранённых изменениях;
- доступность клавиатурой и мобильная навигация;
- истёкшая сессия и безопасный возврат после входа;
- конфликт двух открытых редакторов;
- прежние API не изменяют legacy-хранилище.

### 14.4 Миграция и релиз

- dry-run не меняет БД/S3/файлы;
- один и тот же отчёт применим повторно без дублей;
- итоговые количества и checksums совпадают;
- опубликованные страницы не содержат локальных media URL;
- backup/restore PostgreSQL проверен до переключения;
- inactive slot проходит health, smoke и admin e2e;
- production переключается только отдельным ручным действием.

## 15. Критерии приёмки

Этап готов к ручному production-переключению, когда одновременно выполнены условия:

1. Администратор входит без стандартного пароля через серверную 12-часовую сессию.
2. Любое изменение требует session, CSRF, same-origin и ожидаемую версию записи.
3. Все пять типов контента проходят полный цикл draft → preview → publish → unpublish → revision restore → hard delete.
4. Публичный SSR показывает только опубликованные PostgreSQL-данные без пересборки.
5. Изображения проходят серверную проверку, доступны в адаптивных вариантах из Timeweb S3/CDN и не оставляют битых DB-ссылок при ошибках.
6. Миграционный отчёт подтверждает контент, ревизии, связи и медиа без необъяснённых потерь.
7. Новый образ не изменяет SQLite/SQL.js, Markdown/JSON и локальные uploads через старые API.
8. Unit, integration, SSR и browser tests проходят в CI и в неактивном production-слоте.
9. Перед переключением создан проверенный PostgreSQL backup и сохранён предыдущий immutable образ с его legacy-данными.
10. Само production-переключение не входит в автоматическую сборку и выполняется владельцем вручную после просмотра результата.

## 16. Откат

Откат приложения выполняется переключением Traefik на предыдущий immutable blue/green-образ. Предыдущий образ, SQLite/SQL.js, legacy-файлы и локальные ассеты сохраняются не менее 30 дней. PostgreSQL-миграции этого этапа не откатываются разрушительными DDL-командами во время инцидента: новые таблицы и поля остаются, а предыдущий образ их игнорирует.

Перед переключением создаётся snapshot PostgreSQL. Если после переключения новая админка успела принять изменения, автоматический возврат БД к старому snapshot запрещён, потому что он потеряет эти изменения. Сначала блокируются admin writes, экспортируются новые ревизии и медиа, затем владелец выбирает: исправить новую версию на месте или выполнить контролируемое восстановление с явным пониманием потерь.

S3-объекты content-addressed и не перезаписываются, поэтому возврат приложения не требует удаления новых объектов. Их очистит безопасный orphan sweep после защитного окна и только при отсутствии ссылок в БД.
