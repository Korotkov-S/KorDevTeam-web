# Атомарный выпуск production-контента KorDevTeam — спецификация

Дата: 25 сентября 2026 года.

## Цель

Сделать production-релиз сайта воспроизводимым: один проверенный Git commit должен поставлять не только runtime приложения, но и актуальный управляемый контент из репозитория — статьи, кейсы, услуги, FAQ и их связи.

Успешный результат выглядит так:

1. CI собирает и публикует два неизменяемых образа из одного commit: web runtime и content release tool.
2. Release artifact связывает Git SHA, digest обоих образов и checksum контентного manifest.
3. Перед переключением blue/green-слота deployment создаёт резервную копию, применяет SQL-миграции, строит план контентных изменений и атомарно синхронизирует управляемый контент.
4. Ошибка или конкурентное изменение из админки отменяет всю контентную транзакцию; частично обновлённый каталог невозможен.
5. После проверки контента deployment запускает и проверяет неактивный слот, а затем переключает production-трафик.

## Обнаруженный релизный пробел

Текущий `scripts/deploy-slot.sh` запускает `scripts/migrate-production.mjs`, но этот скрипт применяет только SQL-миграции Drizzle. Он не переносит контент, который хранится в PostgreSQL.

Существующий first-install-инструмент импортирует только исторический набор из 46 статей и 8 кейсов. Он не является полным источником текущего сайта: новые и отредактированные SEO-статьи, полный набор из 23 кейсов, коммерческие услуги, FAQ и связи между материалами применяются отдельными TypeScript-скриптами.

Поэтому публикация одного web-образа может развернуть новый код поверх старого production-контента. CI при этом зелёный, но пользователь не получает весь проверенный результат.

## Выбранный подход

Релиз состоит из двух OCI-образов, собранных из одного и того же commit:

- `web` — существующий production runtime;
- `content-release` — одноразовый инструмент планирования, применения и проверки управляемого контента.

В CI формируется машиночитаемый release manifest. Deployment принимает только точные digest-ссылки, не mutable-теги. Manifest содержит:

- полный Git SHA;
- digest web-образа;
- digest content-release-образа;
- checksum нормализованного контентного manifest;
- версии схемы release manifest и content manifest;
- количество и идентификаторы ожидаемых управляемых записей по типам;
- время сборки и идентификатор CI run.

Контент планируется без записи, затем весь набор изменений применяется одной транзакцией PostgreSQL под единым advisory lock. После commit выполняется независимая проверка фактического состояния базы против manifest.

Это решение выбрано вместо двух альтернатив:

- включение полного toolchain в web-образ увеличило бы production-поверхность атаки и смешало runtime с одноразовыми релизными задачами;
- последовательный запуск существующих sync-скриптов оставил бы три независимые транзакции и мог бы показать пользователям частично обновлённый сайт.

## Границы управляемого контента

Content release управляет только записями, явно перечисленными в source-controlled manifest:

- базовыми материалами исторической миграции, которые остаются частью актуального сайта;
- курируемыми статьями и их SEO-полями;
- полным курируемым портфолио;
- коммерческими услугами;
- FAQ этих услуг;
- связями услуг со статьями и кейсами.

Инструмент не изменяет и не удаляет:

- лиды и обращения;
- администраторов и сессии;
- MCP-токены;
- медиаобъекты и пользовательские загрузки;
- SEO-замеры, коллекции запросов и рекомендации;
- редиректы и системные настройки;
- записи, созданные в админке и не принадлежащие source-controlled manifest.

В первой версии удаления и `retire` нет. Исчезновение ранее управляемого slug из manifest классифицируется как `orphaned-owned` и блокирует релиз. Это предотвращает случайное исчезновение опубликованного материала из-за переименования файла. Явная модель снятия с публикации проектируется отдельно.

## Content manifest

Manifest генерируется детерминированно из источников репозитория. Перед checksum:

- записи сортируются по типу и стабильному идентификатору;
- ключи объектов нормализуются;
- переводы строк приводятся к LF;
- вычисляемые временные поля не включаются;
- ссылки представлены стабильными slug/ID, а не порядком чтения файлов.

Для каждой записи manifest хранит:

- тип и стабильный идентификатор;
- slug;
- желаемый статус публикации;
- checksum нормализованного содержимого;
- ожидаемые связи;
- признак владения source-controlled release;
- при наличии — исходный version/checksum, от которого разрешено обновление.

Общий SHA-256 вычисляется от канонического JSON manifest. Dry-run, apply и verify обязаны получить один и тот же checksum. Изменение файлов между этими этапами завершает release ошибкой.

Количество записей не зашивается в deployment shell-скрипт. Оно берётся из утверждённого manifest, поэтому расширение каталога не требует изменения инфраструктурного кода.

## Защита изменений из админки и MCP

Source-controlled release владеет перечисленными в manifest материалами, но не имеет права молча перезаписывать более свежую production-редакцию.

Для этого в той же транзакции ведётся состояние последнего успешно применённого источника для каждой управляемой записи: entry ID, тип, slug, source checksum, фактический checksum нормализованной строки базы и её version. Во время plan инструмент сравнивает текущую строку с этим сохранённым состоянием. Во время apply он повторно читает строки внутри транзакции с блокировкой и заново проверяет version/checksum. Если материал изменился между plan и apply либо отличается от состояния, зафиксированного последним content release, весь release останавливается с конфликтом.

При первом подключении существующей production-базы действуют строгие правила принятия владения:

- отсутствующая строка планируется как `insert`;
- строка, полностью совпадающая с желаемым source checksum, принимается как `unchanged` и регистрируется при apply;
- существующий slug с отличающимся содержимым считается `unowned-conflict` и не перезаписывается.

Для `unowned-conflict` нет скрытого режима force. Содержимое сначала сравнивается человеком: нужная production-редакция переносится в репозиторий либо запись вручную приводится к утверждённому источнику. После этого строится новый план.

В первой версии флага принудительной перезаписи нет. Конфликт разрешается одним из двух способов:

1. production-изменение переносится в source-controlled источник и собирается новый release;
2. администратор явно возвращает запись к ожидаемому состоянию, после чего deployment запускается повторно.

Отчёт о конфликте содержит тип, slug, ожидаемую и фактическую version/checksum, но не печатает секреты или полный приватный текст в публичные CI-логи.

## Единая транзакция контента

Существующие `applyArticleSources`, `applyPortfolioImport` и `applyCommercialServiceSources` открывают собственные транзакции и используют разные advisory locks. Они должны быть разделены на два слоя:

- внутренние функции принимают существующий transaction/unit of work и не управляют commit;
- текущие публичные обёртки сохраняют самостоятельное поведение для локальных и административных сценариев.

Release orchestrator выполняет в одной транзакции:

1. получает единый глобальный transaction-level advisory lock для content release;
2. повторно строит фактический план и сверяет checksum с dry-run;
3. блокирует изменяемые строки и сохранённое release-состояние, затем проверяет optimistic versions/checksums;
4. синхронизирует статьи;
5. синхронизирует кейсы;
6. синхронизирует услуги и FAQ;
7. создаёт связи услуг со статьями и кейсами;
8. проверяет инварианты manifest до commit;
9. фиксирует release journal с Git SHA, content checksum и результатом.

Порядок обязателен: услуги могут ссылаться на статьи и кейсы, поэтому зависимые связи создаются последними. Любая ошибка откатывает все изменения и запись журнала.

Повторный запуск того же release идемпотентен: план содержит только `unchanged`, новые ревизии не создаются, версии записей не увеличиваются.

## Последовательность production deployment

Deployment выполняет следующие этапы:

1. Проверяет, что web и content-release переданы точными digest-ссылками из release artifact.
2. Проверяет OCI labels обоих образов: repository URL и полный Git revision должны совпадать между собой и с manifest.
3. Проверяет checksum manifest, privacy policy checksum и остальные существующие release approvals.
4. Загружает оба образа до любых изменений production.
5. Создаёт и проверяет резервную копию PostgreSQL.
6. Применяет schema migrations точным web-образом под существующим migration lock.
7. Запускает content dry-run точным content-release-образом и сохраняет приватный структурированный отчёт.
8. Сверяет dry-run с утверждённым content manifest и запрещает неожиданные удаления, конфликты и изменения вне управляемого набора.
9. Запускает атомарный content apply.
10. В новом отдельном процессе запускает content verify и сравнивает production с manifest.
11. Запускает неактивный web-слот, выполняет health/smoke/crawler-проверки и проверку формы обращения.
12. Только после всех проверок переключает web route и фонового worker на новый слот.
13. Записывает deploy evidence: Git SHA, оба digest, content checksum, backup ID, slot и результаты проверок.

Если dry-run или apply завершается ошибкой, неактивный слот не включается и маршрут не переключается. Если verify или smoke завершается ошибкой после успешного content commit, route остаётся на старом слоте и deployment завершается ошибкой.

## Важное ограничение общей базы

Blue и green используют одну PostgreSQL. Поэтому невозможно атомарно переключить одновременно базу и reverse-proxy route без отдельной shadow database или существенно более сложной схемы версионирования.

Принята следующая модель:

- один content apply атомарен внутри PostgreSQL и не показывает частичное состояние;
- успешно применённый контент может стать виден через старый активный слот до переключения route;
- все content/schema изменения обязаны быть обратно совместимы с текущим активным runtime;
- неуспешный новый runtime не вызывает автоматический restore базы: старый слот продолжает обслуживать уже успешно опубликованный, совместимый контент;
- резервная копия и контентные ревизии используются для отдельного ручного восстановления только после анализа причины.

Если будущий релиз требует несовместимого формата контента, он не может проходить через эту схему. Для него сначала выпускается backward-compatible expand-миграция, затем код, и только отдельным поздним релизом выполняется contract-этап.

## Content-release image

Новый Docker target содержит только необходимое для генерации manifest, plan, apply и verify:

- production Node.js runtime;
- скомпилированные release-команды;
- минимальные runtime-зависимости;
- нормализованные источники управляемого контента;
- SQL client и код доменных импортёров.

В образ не попадают development server, браузерные зависимости, Git metadata, тестовые секреты и произвольные shell-инструменты, не нужные release-команде.

Контейнер запускается:

- от непривилегированного UID 1000;
- с read-only root filesystem;
- с временным `tmpfs` только там, где это необходимо;
- только в backend-сети PostgreSQL;
- без опубликованных портов;
- только с `DATABASE_URL` и идентификаторами release;
- без S3, SMTP, CRM, admin session и MCP secrets;
- без разрешённого внешнего egress, если его не требует среда registry pull вне самого контейнера.

## CLI-контракт

Один entrypoint предоставляет четыре явных режима:

- `manifest` — печатает канонические метаданные и checksum без подключения к базе;
- `plan` — читает базу, ничего не меняет и возвращает машинно-читаемый список `insert/update/unchanged/conflict/unowned-conflict/orphaned-owned`;
- `apply` — требует ожидаемый Git SHA и content checksum, повторно планирует и применяет одну транзакцию;
- `verify` — только читает базу и проверяет итог против manifest.

Каждый режим возвращает ненулевой exit code при несовпадении checksum, конфликте, нарушении инварианта или неожиданном изменении. Человеко-читаемый summary пишется отдельно от JSON evidence, чтобы shell orchestration не разбирал свободный текст.

## Первичная установка

`scripts/bootstrap-production-content.sh` переводится на тот же content-release image и тот же manifest. Отдельного legacy-only пути после этого не остаётся.

На пустой базе release сначала создаёт полный актуальный корпус, затем verify проверяет его по manifest. Ожидаемые количества статей, кейсов, услуг и FAQ берутся из manifest, а не из исторических констант `46/8`.

## CI и release artifact

CI должен:

1. собрать web и content-release из одного checkout;
2. проверить revision/source labels;
3. сгенерировать content manifest дважды в чистых процессах и доказать детерминированность;
4. запустить интеграционный content release на чистой базе;
5. запустить повторный apply и доказать идемпотентность;
6. проверить production crawler на полном синхронизированном наборе;
7. опубликовать оба multi-arch образа;
8. получить registry digests и сформировать release artifact только после публикации;
9. сохранить приватные test reports без контента и секретов.

Manual production workflow принимает release artifact либо его точные поля. Mutable tag вроде `main` или `latest` не считается допустимым production input.

## Проверки

Обязательный набор автоматических проверок:

- unit-тест канонизации и детерминированного checksum manifest;
- unit-тест классификации `insert/update/unchanged/conflict/unowned-conflict/orphaned-owned`;
- integration-тест полной синхронизации на чистой базе;
- integration-тест полного rollback, если ошибка возникает на любом шаге после первой записи;
- тест конкурентного изменения между plan и apply;
- тест конфликта с редакцией из админки/MCP;
- тест повторного запуска без новых ревизий;
- тест отсутствия удалений и изменений вне управляемого manifest;
- тест корректного порядка статьи → кейсы → услуги/FAQ → связи;
- тест verify при недостающей записи, неправильном статусе или связи;
- тест content-release container: non-root, read-only, нет публичных портов и лишних секретов;
- тест deploy script: backup предшествует apply, content apply предшествует slot switch, ошибка запрещает switch;
- тест release gate: оба digest принадлежат одному Git SHA и checksum совпадает с artifact;
- полный build, server tests, crawler и smoke на синхронизированном корпусе.

## Наблюдаемость и аудит

В PostgreSQL добавляются две служебные таблицы.

`content_release_runs` хранит:

- release ID;
- Git SHA;
- content checksum;
- количество insert/update/unchanged;
- actor `deployment`;
- committed at.

`content_release_items` хранит последнее успешно применённое состояние каждой управляемой записи:

- entry ID, тип и slug;
- release ID;
- source checksum;
- checksum нормализованного состояния в базе;
- database version после apply.

Обе таблицы обновляются в той же транзакции, что и контент. Неуспешный release не оставляет ложного состояния владения.

Секреты, полный текст статей и Bearer-токены в журнал не записываются. Deployment-логи содержат только идентификаторы, slug конфликтов, counts, checksums и безопасные коды ошибок.

## Критерии готовности

Функция считается готовой, когда:

1. два точных образа одного commit опубликованы и связаны release artifact;
2. полная актуальная база разворачивается с нуля одним content-release инструментом;
3. обновление существующей базы атомарно и не перезаписывает неизвестные правки;
4. повторный запуск не создаёт лишних изменений;
5. deployment невозможно переключить на новый слот после неуспешного content release;
6. старый активный runtime корректно обслуживает новый контент в общей базе;
7. production evidence однозначно отвечает, какой код и какой набор контента опубликованы;
8. legacy bootstrap больше не создаёт урезанный каталог.

## Дальнейшие возможности, не входящие в первую версию

- shadow database для действительно атомарного переключения route и данных;
- явно утверждаемые destructive retire/delete операции;
- UI просмотра content release plan в админке;
- автоматическое формирование source patch из production-правки MCP;
- криптографическая подпись release manifest и проверка provenance/SBOM admission-контроллером.
