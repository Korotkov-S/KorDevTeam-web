# Автономный GEO-сбор KorDevTeam — дополнение к спецификации

## Причина изменения

Первый GEO-контур предполагал, что авторизованный чат-агент получает реальные ответы AI-платформ и записывает их через MCP. Такой сценарий подходит для ручной проверки, но не для ежедневного запуска без человека: браузерный интерфейс может запросить подтверждение отправки и завершить цикл с `0 из 3` наблюдений.

Ежедневная автоматизация не должна считать отсутствие браузерного подтверждения неисправностью сайта и не должна сохранять искусственные нулевые показатели.

## Принятое разделение

GEO-сбор делится на два независимых контура.

1. **Серверный ежедневный контур** всегда собирает только показатели, доступные без браузерной сессии: AI-referral из Яндекс Метрики и crawler health. Эти показатели уже входят в `seo-job` и продолжают обновляться ежедневно.
2. **Контрольные ответы AI-платформ** собираются только через официальные API конкретного поставщика. Для каждого API создаётся отдельный provider с собственным включателем и секретом в `/etc/kordevteam/operations.env`. Отключённый или не настроенный provider имеет статус `disabled`, а не `failed`.

Автоматизированный вход в пользовательские интерфейсы, хранение cookies, обход подтверждений и браузерный скрейпинг не используются.

## Поведение до подключения API

- ежедневный SEO/GEO-запуск обновляет Вебмастер, Search Console, Метрику и crawler health;
- MCP используется для чтения накопленной GEO-истории, анализа рефералов и crawler health;
- `start_geo_run`, `record_geo_observation` и `finish_geo_run` не вызываются без фактически полученных API-ответов;
- отсутствие нового controlled-answer run отображается как «поставщик не подключён / новых наблюдений нет», а не как нулевая видимость;
- рекомендации по упоминаниям, цитированиям и Share of Voice не создаются без полного сопоставимого набора.

## Provider API

Каждый будущий provider обязан:

- явно маркировать `platform`, `surface`, `mode`, `language`, `region` и версию модели или endpoint;
- выполнять ровно три независимых запроса для каждого выбранного prompt;
- возвращать исходный ответ, ссылки и доступные provider metadata в ограниченном размере;
- разделять `disabled`, `partial` и `failed` безопасными кодами;
- не считать отсутствие упоминания ошибкой и не считать отсутствие ответа нулевым наблюдением;
- проходить fixture-тесты без реального расходования API-квоты.

Ответы разных API или поверхностей не сравниваются между собой. Например, API-ответ с web grounding не выдаётся за результат пользовательского интерфейса ChatGPT Search.

## Запись и безопасность

Серверный worker использует существующий lifecycle `geo_runs` напрямую через доменный сервис или отдельного service principal. Он не имитирует пользовательский MCP-токен. Секреты доступны только изолированному collector service, не попадают в web, admin, MCP-ответы, логи и метаданные запуска.

Если provider начинает платный запрос, для него задаются дневной лимит, ограничение полного prompt-набора и отдельный таймер. Повторный запуск не должен дублировать наблюдения или превышать лимит.

## Этапы внедрения

1. Немедленно убрать controlled-answer browser loop из ежедневного задания; оставить работающие first-party показатели.
2. Добавить provider-neutral worker и состояние `disabled` для не подключённых AI API.
3. Подключать поставщиков по одному после получения официального API-доступа и отдельного подтверждения стоимости.
4. После первого полного трёхкратного снимка включить сопоставление с предыдущими полными снимками.

## Критерии готовности

- ежедневный запуск больше не завершается `0 из 3` из-за браузерного подтверждения;
- SEO, AI-referral и crawler health продолжают обновляться независимо;
- без API-ключа controlled-answer сбор явно отключён и не создаёт ложных нулей;
- при подключённом provider полный run содержит три наблюдения на каждый prompt и завершается атомарно;
- админка и MCP различают отсутствие поставщика, ошибку поставщика и фактическое отсутствие упоминания.
