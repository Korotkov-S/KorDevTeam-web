# MCP-доступ к контенту KorDevTeam — спецификация

Дата: 25 сентября 2026 года.

## Цель

Добавить в административную панель KorDevTeam выпуск персональных токенов и предоставить один постоянный Streamable HTTP MCP-адрес, через который Codex сможет читать и изменять тексты сайта, загружать изображения и явно публиковать подготовленные материалы.

Решение предназначено для личного подключения владельца сайта из Codex. Оно не является публичной интеграционной платформой и не должно требовать OAuth 2.1 на первой итерации.

Успешный результат выглядит так:

1. Администратор открывает `/admin/mcp/`, выпускает токен и видит его только один раз.
2. В Codex настраивается адрес `https://kordev.team/mcp` и имя переменной окружения с Bearer-токеном.
3. Codex получает список разрешённых инструментов, читает существующий материал, загружает изображение, сохраняет черновик и отдельной командой публикует его.
4. Все изменения проходят существующую валидацию, создают штатные ревизии и очищают контентные кеши.
5. Токен можно немедленно отозвать в административной панели.

## Исходное состояние

- Сайт работает на React Router 7 и Express.
- Административная панель использует PostgreSQL-сессии, cookie, CSRF-проверку и активного `admin_users`.
- Контент типов `service`, `case`, `article`, `page` и `faq` хранится в `content_entries`.
- `createAdminContentService` уже предоставляет чтение, сохранение, снятие с публикации и восстановление ревизий.
- Сохранение использует optimistic concurrency через `expectedVersion`, создаёт `content_revisions` и обновляет связи и ссылки на медиа в одной транзакции.
- `createMediaService` уже проверяет и преобразует JPG, PNG и WebP, сохраняет файлы в S3-совместимое хранилище и записывает метаданные в PostgreSQL.
- Публичного API для административного контента и MCP-сервера нет.
- Пакеты MCP SDK `@modelcontextprotocol/server`, `@modelcontextprotocol/node` и Express-адаптер пока не установлены.

## Выбранный подход

MCP-сервер встраивается в существующий Node.js runtime и монтируется на `/mcp` до React Router SSR-обработчика. Реализация использует стабильную линию 2.1 официального TypeScript SDK (`@modelcontextprotocol/server`, `@modelcontextprotocol/node`, `@modelcontextprotocol/express`) и Streamable HTTP transport. Обработчик обслуживает современный протокол и штатный stateless fallback для MCP-клиентов предыдущей версии.

MCP-слой не обращается к таблицам контента и объектному хранилищу напрямую. Он аутентифицирует токен, проверяет права и вызывает существующие `AdminContentService` и `MediaService`. Узкий адаптер преобразует MCP-входы в уже существующие команды административного домена и преобразует доменные ошибки в безопасные MCP-ответы.

Это решение выбрано вместо двух альтернатив:

- отдельный MCP-сервис потребовал бы отдельного деплоя, соединения с базой, конфигурации S3 и синхронизации доменной логики;
- промежуточный REST API расширил бы поверхность атаки и продублировал интерфейс, который в первой итерации нужен только MCP-клиенту.

## Границы первой версии

В первую версию входят:

- выпуск, просмотр списка и отзыв персональных MCP-токенов;
- Bearer-аутентификация MCP-запросов;
- чтение контента и медиатеки;
- создание и изменение черновиков;
- загрузка изображений;
- отдельные команды публикации и снятия с публикации;
- работа со всеми существующими типами контента;
- аудит использования токенов и сохранение штатных контентных ревизий.

В первую версию не входят:

- OAuth 2.1 и подключение в качестве ChatGPT app;
- удаление контента или изображений через MCP;
- отдельное серверное хранение незавершённой редакции поверх уже опубликованного материала;
- управление администраторами, настройками сайта, редиректами и лидами;
- загрузка изображений по внешнему URL;
- массовая публикация или пакетный импорт;
- legacy SSE transport;
- передача токена в query string или непосредственно в URL подключения.

## Модель токенов

Добавляется таблица `mcp_tokens`:

- `id` — UUID токена;
- `admin_user_id` — администратор, выпустивший токен;
- `name` — понятное имя, например `Codex MacBook`;
- `token_hash` — 64-символьный hex HMAC-SHA-256;
- `token_prefix` — безопасный короткий префикс для идентификации токена в интерфейсе;
- `scopes` — массив разрешений;
- `created_at` — время выпуска;
- `last_used_at` — время последней успешной аутентификации;
- `expires_at` — необязательный срок действия;
- `revoked_at` — время отзыва.

Токен имеет формат `kdt_mcp_<43 base64url-символа>`. Секретная часть создаётся из 32 криптографически случайных байтов. Для поиска в базе используется HMAC-SHA-256 с существующим серверным ключом с отдельным доменом `mcp-token`; открытое значение не сохраняется.

Полный токен возвращается браузеру только в ответе на создание и больше не может быть получен с сервера. Ответ создания содержит `Cache-Control: no-store`. Страница списка показывает имя, префикс, права, дату создания, последнее использование, срок действия и состояние отзыва.

Доступные права:

- `content:read` — список и чтение материалов;
- `content:write` — создание и изменение черновиков;
- `content:publish` — публикация и снятие с публикации;
- `media:read` — чтение медиатеки;
- `media:write` — загрузка изображений.

В форме выпуска все пять прав включены по умолчанию, но администратор может снять ненужные. Срок действия выбирается из 30, 90 или 365 дней либо `без срока`; по умолчанию — 365 дней. Отозванный, просроченный или принадлежащий неактивному администратору токен немедленно перестаёт работать.

Администратор, выпустивший токен, становится actor для контентных ревизий и загруженных медиа. Это сохраняет совместимость с существующими внешними ключами `content_revisions.admin_user_id` и `media_assets.created_by`.

## Административный интерфейс

Добавляется пункт `MCP-доступ` в существующее меню и маршрут `/admin/mcp/` внутри защищённого admin layout.

Страница содержит:

1. Постоянные адреса подключения:
   - production: `https://kordev.team/mcp`;
   - локальная разработка: адрес текущего origin с путём `/mcp`.
2. Готовый фрагмент конфигурации Codex без самого секрета:

       [mcp_servers.kordev_site]
       url = "https://kordev.team/mcp"
       bearer_token_env_var = "KORDEV_MCP_TOKEN"

3. Форму выпуска: имя, набор прав и срок действия.
4. Одноразовый блок нового токена с кнопкой копирования и предупреждением сохранить его сейчас.
5. Список ранее созданных токенов и действие `Отозвать`.

Создание и отзыв доступны только через существующую cookie-сессию администратора, same-origin и CSRF-проверку. Через сам MCP новые токены выпускать нельзя.

## MCP transport и HTTP-контракт

- Единственный endpoint: `/mcp`.
- Основной production URL: `https://kordev.team/mcp`.
- Транспорт: Streamable HTTP из официального MCP SDK.
- Операции не требуют серверного состояния между вызовами, поэтому transport работает stateless.
- Авторизация проверяется на каждом запросе по заголовку `Authorization: Bearer <token>`.
- Токены из query string, cookie или тела запроса не принимаются.
- MCP-ответы и ошибки получают `Cache-Control: no-store`.
- Endpoint не использует общий JSON body parser до MCP transport, чтобы SDK получил исходный запрос в ожидаемом формате.
- Размер MCP-запроса ограничивается с учётом base64-накладных расходов для существующего лимита изображения 20 МБ.
- CORS не открывается произвольным browser origin; штатный серверный MCP-клиент не требует CORS.

Отсутствующий, неправильный, отозванный или просроченный токен даёт HTTP 401. Сервер регистрирует для конкретного соединения только инструменты, разрешённые scopes токена; принудительный вызов незарегистрированного инструмента завершается стандартной MCP-ошибкой и не достигает доменного сервиса. Нарушение MCP-протокола обрабатывает SDK. Доменные ошибки инструментов возвращаются как безопасные MCP tool errors с машинным кодом и коротким сообщением без stack trace, SQL и конфигурационных данных.

## Набор MCP-инструментов

### `list_content`

Право: `content:read`.

Вход:

- необязательные `kind`, `status`, `query`;
- `limit` с ограниченным верхним пределом;
- необязательный cursor для постраничного чтения.

Выход: компактные записи с `id`, `kind`, `slug`, `status`, `title`, `version`, `updatedAt` и `publishedAt`.

### `get_content`

Право: `content:read`.

Принимает UUID либо пару `kind` + `slug`. Возвращает полное текущее состояние редактора: поля записи, relations, mediaRefs и текущую `version`. История ревизий в ответ не включается.

### `create_content_draft`

Право: `content:write`.

Принимает полный валидируемый набор полей нового материала, relations и mediaRefs. Всегда создаёт `draft`, даже если клиент передаст другое намерение. Возвращает UUID, slug, status и version.

### `update_content_draft`

Права: `content:read` и `content:write`.

Принимает UUID, `expectedVersion` и полный следующий снимок редактируемых полей, relations и mediaRefs. Полный снимок выбран вместо неоднозначного глубокого merge поля `payload`. Перед сохранением используются существующие `parseAdminContentCommand` и доменные проверки. Инструмент работает только с записью, которая уже находится в статусе `draft`, и оставляет её черновиком.

Клиент должен сначала вызвать `get_content`, сохранить неизменяемые значения и передать полученную version. Конфликт версии не перезаписывает чужие изменения и возвращает `content_version_conflict`.

Попытка сохранить опубликованную запись этим инструментом возвращает `content_not_draft` и ничего не меняет. Это защищает страницу от неявного снятия с публикации: текущая модель `content_entries` не хранит отдельную незавершённую редакцию поверх опубликованной версии.

### `publish_content`

Право: `content:publish`; если передаётся изменённый снимок, дополнительно требуется `content:write`.

Принимает UUID, `expectedVersion` и необязательный полный снимок редактируемых полей, relations и mediaRefs. Сервер повторно загружает актуальное редакторское состояние, требует совпадения версии и запускает существующую полную проверку публикации.

- Для существующего черновика снимок можно не передавать: сервер публикует уже сохранённое состояние.
- Для изменения уже опубликованного материала Codex сначала читает текущую запись, готовит текст локально и затем передаёт полный новый снимок в `publish_content`. Обновление и сохранение статуса `published` происходят атомарно в одной штатной транзакции с ревизией.

Таким образом, изменение опубликованной страницы не появляется на сайте до явного вызова publish-инструмента и не требует временно снимать страницу с публикации. Незавершённый вариант до вызова хранится в рабочем контексте клиента; отдельное серверное хранилище таких вариантов не создаётся в первой версии.

### `unpublish_content`

Право: `content:publish`.

Принимает UUID и `expectedVersion`, вызывает существующий `unpublish` и возвращает следующую version.

### `list_media`

Право: `media:read`.

Возвращает список доступных публичных изображений с UUID, URL, mime type, размерами, alt-текстом, decorative, version и датой создания. Результат ограничивается и поддерживает поиск по alt-тексту и постраничное чтение.

### `upload_image`

Право: `media:write`.

Принимает:

- `filename`;
- `mimeType`;
- `base64Data`;
- `altText`;
- `decorative`.

Base64 декодируется только после проверки формата и размера. Затем данные передаются существующему `MediaService.upload`, поэтому сохраняются текущие ограничения форматов, 20 МБ, 40 мегапикселей, дедупликация, создание вариантов и очистка временных объектов. Инструмент возвращает UUID, public URL, размеры, mime type и version.

Внешние URL сервер не скачивает, чтобы не создавать SSRF-поверхность.

## Поток данных

1. Codex отправляет MCP-запрос на `/mcp` с Bearer-токеном.
2. HTTP-слой проверяет формат токена и вычисляет доменно-разделённый HMAC.
3. Репозиторий находит активный токен, проверяет администратора, срок и отзыв, затем обновляет `last_used_at`.
4. Для вызова инструмента проверяются требуемые scopes.
5. Zod-схема MCP-инструмента ограничивает форму и объём входа.
6. Адаптер вызывает существующий сервис контента или медиатеки с `admin_user_id` владельца токена.
7. Существующие транзакции, optimistic concurrency, ревизии, S3-обработка и инвалидация кешей выполняются без альтернативного пути записи.
8. MCP возвращает компактный текстовый результат и `structuredContent`, пригодный для следующего автоматизированного шага.

## Ошибки и безопасность

- Секреты не записываются в логи, базу в открытом виде, URL, HTML после перезагрузки или конфигурационный фрагмент.
- Стандартный серверный лог сохраняет метод и path, но не `Authorization` и не MCP arguments.
- Структурированный серверный лог MCP-вызова содержит token ID, admin user ID, имя инструмента, время, длительность, статус и безопасный код ошибки; отдельная таблица аудита не создаётся. Тексты материалов и base64 изображения не логируются.
- Проверки прав выполняются до разбора большого содержимого инструмента, насколько это допускает transport SDK.
- Неизвестные поля во входах отклоняются.
- Выборки имеют верхние пределы; неограниченного экспорта нет.
- Все операции записи требуют optimistic concurrency там, где запись уже существует.
- Публикация отделена от редактирования, поэтому обычный write-токен не может сделать материал публичным.
- У MCP отсутствуют destructive-инструменты.
- При неожиданной ошибке клиент получает общий `internal_error`, а подробность остаётся только в серверном структурированном логе.

## Компоненты и размещение ответственности

### `src/server/mcp/tokenRepository.ts`

Только запросы к `mcp_tokens`: создание, список, поиск активного токена, обновление последнего использования и отзыв.

### `src/server/mcp/tokenService.ts`

Генерация и HMAC токена, валидация имени/scopes/срока, аутентификация Bearer и представление безопасных данных для административной страницы.

### `src/server/mcp/tools.ts`

Zod-контракты и регистрация инструментов. Здесь нет SQL или S3-вызовов; инструменты работают через переданные сервисы.

### `src/server/mcp/http.ts`

Создание Streamable HTTP router, проверка Authorization, создание MCP server на запрос, маппинг транспортных ошибок и безопасное логирование.

### `src/server/mcp/runtime.ts`

Production wiring: база, token service, admin content service, media service и конфигурация.

### `src/routes/admin/mcp.tsx` и `src/routes/admin/mcp.server.ts`

Защищённая административная страница и её loader/action. Они используют существующие admin auth, CSRF и headers.

### `server/runtime.mjs` и `src/entry.server.tsx`

Экспорт и подключение MCP router перед SSR. Публичные маршруты и существующие `/api` остаются без изменений.

## Изменения базы и миграция

Drizzle schema расширяется таблицей `mcp_tokens`, индексами по `token_hash`, `admin_user_id`, `expires_at` и активному состоянию. Создаётся следующая append-only миграция `drizzle/0004_mcp_tokens.sql` и обновляется Drizzle journal.

Миграция не изменяет существующие строки и может быть применена до выкладки кода. Откат приложения безопасен: старая версия игнорирует новую пустую или заполненную таблицу. Удалять таблицу при откате приложения не требуется.

Production readiness-проверка должна требовать наличие новой таблицы после миграции. Резервное копирование должно включать её в inventory, но секретов открытого вида в ней нет.

## Конфигурация Codex

Администратор копирует токен в переменную окружения локальной машины:

    export KORDEV_MCP_TOKEN='kdt_mcp_...'

В конфигурации Codex хранится только имя переменной:

    [mcp_servers.kordev_site]
    url = "https://kordev.team/mcp"
    bearer_token_env_var = "KORDEV_MCP_TOKEN"

Для локальной проверки URL меняется на `http://127.0.0.1:3003/mcp`. Токен не помещается в `config.toml` и не передаётся в адресе.

## Тестирование

### Токены

- формат и криптографическая случайность выпуска;
- в базе отсутствует открытый токен;
- аутентификация активного токена;
- отказ для неправильного, отозванного и просроченного токена;
- отказ при деактивации администратора;
- проверка каждого scope;
- обновление `last_used_at` без раскрытия секрета;
- CSRF и same-origin для выпуска и отзыва;
- одноразовое отображение секрета и `Cache-Control: no-store`.

### MCP protocol

- initialize и `tools/list` через Streamable HTTP;
- 401 без Bearer-токена и 403 без нужного scope;
- успешный `tools/call` для каждого инструмента;
- неизвестный инструмент и невалидный input;
- отсутствие delete-инструментов;
- отсутствие секретов и аргументов в логах.

### Контент

- list/get для каждого существующего kind;
- создание только draft;
- обновление создаёт ревизию и увеличивает version;
- черновое обновление опубликованной записи отклоняется и не снимает её с публикации;
- stale `expectedVersion` возвращает конфликт и не меняет запись;
- публикация выполняет полную текущую валидацию;
- атомарное изменение опубликованного материала доступно только через `publish_content` с правами write и publish;
- publish/unpublish создают ожидаемую историю и очищают кеши;
- права `content:write` без `content:publish` не позволяют публикацию.

### Медиа

- загрузка разрешённых форматов;
- отказ для неправильного MIME, сигнатуры, размера, pixel count и base64;
- обязательный alt-текст для недекоративного изображения;
- дедупликация и возврат публичного URL;
- временные и частично созданные объекты очищаются при ошибке;
- отсутствует загрузка по URL и удаление через MCP.

### Общая проверка

- `yarn typecheck`;
- полный `yarn test`;
- production `yarn build`;
- smoke-подключение локального Codex к `http://127.0.0.1:3003/mcp`;
- smoke-подключение production Codex после миграции и выпуска отдельного production-токена.

## Критерии приёмки

1. Администратор может выпустить токен, скопировать его один раз, увидеть безопасную запись в списке и отозвать её.
2. В PostgreSQL нет открытого значения токена.
3. Codex подключается к одному URL `/mcp` с Bearer-токеном из переменной окружения.
4. Набор инструментов позволяет прочитать материал, создать или изменить черновик, загрузить изображение и отдельно опубликовать результат.
5. MCP не предоставляет удаление контента или медиа.
6. Изменения используют существующие доменные сервисы, версионирование, ревизии, авторство и кеш-инвалидацию.
7. Отозванный токен перестаёт работать со следующего запроса.
8. Ошибки не раскрывают секреты, содержимое файлов, SQL, stack trace или серверную конфигурацию.
9. Все автоматические проверки и оба smoke-сценария проходят.

## Последующее расширение
