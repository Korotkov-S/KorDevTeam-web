# Миграция русского legacy-контента

Команды запускаются из корня репозитория:

```sh
DATABASE_URL=postgresql://kordev:kordev@localhost:5433/kordev yarn content:migrate --dry-run
DATABASE_URL=postgresql://kordev:kordev@localhost:5433/kordev yarn content:migrate --batch-id legacy-ru-p0
DATABASE_URL=postgresql://kordev:kordev@localhost:5433/kordev yarn content:verify --batch-id legacy-ru-p0
```

`--root PATH` задаёт корень источников, `--sqlite-path PATH` — путь к legacy SQL.js базе (относительно корня или абсолютный). По умолчанию читается `server/data/content.sqlite`; файл открывается из копии байтов в памяти и никогда не сохраняется. Храните оригинал до контрольной точки P0. Отсутствующие таблицы/записи дополняются из `public/blog`, затем `src/blog`, а проекты — из `public/content/projects.ru.json`. `public/content/blog.ru.json` дополняет метаданные статей. Английские строки и файлы исключаются.

Приоритет текста и полей записи — SQLite, затем deployed Markdown/JSON. Недостающие SEO/медиа-поля SQLite дополняются из русского индекса. Проектные ID нормализуются в slug; коллизии блокируют импорт. Содержимое кейсов сохраняет описание, возможности, технологии, изображения и ссылки в Markdown. Статьи сохраняют теги, обложку, список изображений и время чтения в строгом payload.

Для миграции действует исключение из обычной публикации: `publishedAt` берётся из распознанной даты публикации, затем `createdAtMs`; `updatedAt` — из `updatedDate`, затем `updatedAtMs`, `mtimeMs` или даты публикации. Для строк SQLite явный `updated_at_ms` имеет приоритет над датой из индекса. `createdAt` использует историческую дату публикации, затем известную дату создания/обновления. Если исторических данных нет, используется время вставки/публикации. Обычный сервис публикации не изменён. Публичные пути изображений остаются URL в payload; перенос медиа в объектное хранилище выполняется отдельно.

Импорт проходит одной PostgreSQL-транзакцией: строгая валидация → draft версии 1 → снимок ревизии → published версии 2. Ревизии миграции имеют `adminUserId = null`. Advisory lock сериализует конкурирующие импорт-пакеты. Manifest с SHA-256 и идентификаторами записей хранится в `site_settings`. Повтор идентичного пакета не создаёт записей или ревизий. Изменённый источник под тем же batch ID и несовпадающая целевая запись блокируют весь пакет; существующее содержимое не перезаписывается.

Без `--batch-id` используется ID на основе SHA-256 пакета. Для последующей проверки изменений источников указывайте фиксированный batch ID. Контрольные суммы учитывают канонические исходные данные, связанные метаданные и результат преобразования; ключи объектов сортируются, файловое время запуска не используется. Генерация нового индекса с изменёнными метаданными, включая `mtimeMs`, изменит checksum.

В stdout выводится JSON; сообщения диагностики идут в stderr. Код выхода: `0` — успешно, `2` — ошибки данных/коллизии/несовпадение проверки, `1` — ошибка запуска или соединения. `--dry-run` не пишет в PostgreSQL; при заданном `DATABASE_URL` он также проверяет целевые коллизии. Без URL dry-run проверяет только источники. Сохраняйте отчёты вне репозитория или как CI-артефакты. Проверка сравнивает пакет с источниками, manifest, содержимым, статусом и историческими датами записей; посторонний контент других пакетов допустим.
